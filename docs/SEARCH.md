# Search in a self-hosted installation

App Search is required for Docsie's existing search workflows. From
platform chart `0.2.0-preview.4`, the basic KB profile includes it; an AI model
or the full Dokuta profile is not required to install search.

## What is packaged

- Elastic's ECK operator chart and CRDs, vendored at `2.16.1` with its license.
- Elasticsearch and Enterprise Search/App Search, both pinned to `8.12.0`.
- An automatic bootstrap Job that creates a private indexing key and a separate
  read-only private key for signing filtered portal searches.
- Docsie endpoint configuration, required Secret references and verified internal
  TLS using ECK's generated certificate.
- A Helm test that indexes a disposable document, retrieves it through search,
  verifies signed search filters and that the signing key cannot write, and
  deletes the test engine.

The operator is a separate cluster prerequisite, installed automatically by the
explicit-cluster installer. It is not removed when the Docsie release is removed.
An existing ECK installation is reused; its operator must support Enterprise
Search and watch the target namespace. The installer does not overwrite existing
Elastic CRDs owned by another installation.

## Install

Prepare the application image access, persistent storage and normal Docsie values
as described in [Kubernetes installation](INSTALL_KUBERNETES.md), then run:

```bash
bash scripts/install-kubernetes.sh /absolute/path/to/kubeconfig docsie /absolute/path/to/values.yaml
```

This installs ECK first if absent, installs Docsie plus search, waits for the
search bootstrap and application readiness, and runs the focused App Search Helm test.

For direct Helm use, install the prerequisite first:

```bash
bash scripts/ensure-search-operator.sh /absolute/path/to/kubeconfig
helm dependency build charts/docsie-platform --skip-refresh
helm upgrade --install docsie charts/docsie-platform \
  --kubeconfig /absolute/path/to/kubeconfig --namespace docsie --create-namespace \
  --values /absolute/path/to/values.yaml --wait --wait-for-jobs --timeout 20m
helm test docsie --filter name=docsie-search-test --kubeconfig /absolute/path/to/kubeconfig --namespace docsie --logs
```

## Browser access

The in-cluster indexing endpoint is `https://production-ent-http:3002/api/as/v1`.
Portal searches also need a browser-reachable search endpoint. The default
advertised endpoint is `https://search.<global.hostname>/api/as/v1`.
Configure DNS and a browser-trusted TLS certificate before sharing a portal.
For an existing nginx ingress controller:

```yaml
global:
  hostname: docs.example.com
  appSearch:
    publicHost: search.docs.example.com/api/as/v1
elastic-appsearch-onprem:
  ingress:
    enabled: true
    className: nginx
    tlsSecretName: docsie-search-tls
```

Create that TLS Secret using your certificate manager or existing certificate
workflow. The chart exposes only the App Search API route, not the administrative
UI. Other ingress implementations need their equivalent HTTPS-backend routing.
For an isolated local API test, the focused Helm search test works without ingress or DNS.

## Existing full-profile Chroma data

This chart also corrects the Chroma volume mount: earlier charts created `db-data`
but did not attach it to the container. Before upgrading an existing full-profile
installation, preserve `/chroma/chroma` from the running Chroma container and
restore it to the intended PVC. Back up SQLite consistently and preserve any
associated index directories. Stop writes during the migration. Mounting a new,
empty PVC alone does not migrate an old container's data. Fresh installations use
the PVC automatically.

## Credentials and upgrades

The bootstrap Job keeps named credentials stable across upgrades. Docsie receives
`APPSEARCH_KEY` and `APPSEARCH_SEARCH_KEY` from `<release>-appsearch-runtime`.
The read-only private signing key remains server-side; do not publish it as a
browser API key. Signed, filtered tokens are generated by Docsie's application.
The Elasticsearch administrator password is mounted only into the bootstrap Job,
not into the Docsie workloads.

Back up Elasticsearch data and the generated ECK/runtime Secrets together. If
stored runtime keys differ from the server's named keys, bootstrap fails rather
than silently rotating credentials. Recover the matching data/Secrets before
retrying. Fresh installation generates credentials without copying hosted keys.

For an existing external App Search deployment, set
`global.appSearch.enabled: false` and supply all `APPSEARCH_*` endpoints, TLS and
Secret-backed credentials through the Docsie chart's environment configuration.
Disabling the bundled service does not remove the application's need for search.

## Sizing and limitations

Default search requests are 2 GiB for Elasticsearch plus 2 GiB for Enterprise
Search, in addition to the operator and the rest of Docsie. These are reservations,
not a measured minimum. The older plain Elasticsearch service remains because
Docsie also has a separate Elasticsearch integration; replacing or consolidating
it requires application-level validation.

This is preview packaging, not proof that every portal or AI retrieval
workflow has passed. The earlier 8-GiB basic rehearsal excluded App Search.
See [sizing](SIZING_AND_COST.md) and [release status](RELEASE_STATUS.md).

Image manifests for search are explicit in the chart, so the image checker can
include them and the operator. A complete offline image bundle remains unreleased;
source charts alone do not supply container layers. Do not upgrade Enterprise
Search to a different major version as an image-only change.

Upstream references: [ECK Helm installation](https://www.elastic.co/docs/deploy-manage/deploy/cloud-on-k8s/install-using-helm-chart),
[App Search authentication](https://www.elastic.co/guide/en/app-search/8.19/authentication.html),
[Credentials API](https://www.elastic.co/guide/en/app-search/8.19/credentials.html).

## Validation recorded 2026-09-07

- Installed the vendored ECK operator and a fresh search stack in an isolated
  local namespace. Automatic credential bootstrap completed without manual keys.
- Reinstalled/upgraded that search chart twice; the stored credential hash stayed
  unchanged. Indexing, search retrieval, signed-filter enforcement and rejection
  of writes using the read-only key passed against the real service.
- Upgraded the existing local Docsie release with the explicit-cluster wrapper.
  It completed at revision 8, including migration/bootstrap hooks and the focused
  search test. All 18 service pods were ready. This was an existing-install upgrade,
  not a fresh complete-platform installation.
- Docsie's actual `create_appsearch_client` authenticated using its configured
  endpoint and certificate verification against the bundled service.
- Preserved the local Chroma SQLite database before attaching its PVC; integrity
  checks passed after restore and restart. It contained zero collections.
- All four search/operator/bootstrap image manifests support AMD64 and ARM64.
  Runtime testing used ARM64 search containers; the Docsie app remained emulated.
- Thirteen distribution/bootstrap tests, Helm lint, distribution audit and chart
  packaging passed.

The local Docker VM had 8 GiB RAM. For this test, Elasticsearch had a 1-GiB limit,
and Enterprise Search used a 768-MiB JVM heap with a 2-GiB limit. These overrides
are below the chart defaults. No inference load, concurrency benchmark or
browser-facing portal search acceptance was performed; this is not a measured
hardware minimum. Existing vendored Dokuta test hooks are outside the focused
search check. A fresh full-platform install and public-image completion remain
separate release checks.
